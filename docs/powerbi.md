# Power BI (§103–104)

Power BI Desktop connects directly to the Gold and ops tables through the Databricks SQL
warehouse. Gold → Power BI, nothing in between (§103).

## 0. Fastest path: the generated project

`powerbi/ekadai.pbip` is generated by `powerbi/generate_pbip.py` from the live table schemas
(`powerbi/columns.txt`). It contains all tables, relationships, measures, and the 9 pages below.
1. Open it in Power BI Desktop.
2. Sign in when asked: **Azure Databricks → Microsoft Entra ID / OAuth**, with your Azure
   account.
3. Click **Refresh**.

- Regenerate for a live demo:
  `python powerbi/generate_pbip.py --columns powerbi/columns.txt --mode directquery`, then turn
  on *Format page → Page refresh* in Desktop.
- If Desktop asks, enable *Options → Preview features → Power BI Project (.pbip)*, *TMDL* and
  *PBIR*.

Sections 1–4 describe the same thing for building or adjusting it by hand.

## 1. Connect

1. Power BI Desktop → **Get data** → **Azure Databricks**.
2. **Server hostname**: `adb-7405617818071366.6.azuredatabricks.net`
3. **HTTP path**: `/sql/1.0/warehouses/68d5a8cb07485e9a`
4. **Data connectivity mode**:
   - **Import** for building the report. The warehouse only runs during refresh, which matters
     on a credit budget.
   - **DirectQuery** for a live, real-time demo (the warehouse runs while the report is
     open).
5. Sign in with **Azure Active Directory** (the same account as the workspace).
6. Select the tables in catalog `ekadai_databricks`:
   - schema **gold**: every `dim_*`, `fact_*` and `agg_*` table;
   - schema **ops**: `pipeline_runs`, `pipeline_stage_metrics`, `latency_metrics`,
     `data_quality_metrics`, `reference_resolution_status`, `late_replay_status`,
     `kafka_lag`, `cdc_connector_health`, `backfill_audit`, `reconciliation_results`.

The SQL warehouse auto-stops after 1 minute idle, so the first query after a pause takes a few
seconds to wake it.

## 2. Model (star schema)

Relationships are single direction, dimension → fact, many-to-one:

| From (many) | To (one) |
|---|---|
| `fact_events[user_key]` | `dim_user[user_key]` |
| `fact_events[product_key]` | `dim_product[product_key]` |
| `fact_events[category_key]` | `dim_category[category_key]` |
| `fact_events[device_key]` | `dim_device[device_key]` |
| `fact_events[date_key]` | `dim_date[date_key]` |
| `fact_sessions[user_key]` / `[device_key]` / `[date_key]` | `dim_user` / `dim_device` / `dim_date` |
| `fact_orders[user_key]` / `[date_key]` | `dim_user` / `dim_date` |
| `fact_order_items[order_key]` | `fact_orders[order_key]` |
| `fact_order_items[product_key]` / `[user_key]` / `[date_key]` | `dim_product` / `dim_user` / `dim_date` |
| `dim_product[category_key]` | `dim_category[category_key]` |
| `agg_*[date_key]` | `dim_date[date_key]` |
| `agg_product_performance[product_key]` | `dim_product[product_key]` |
| `agg_user_activity[user_key]` | `dim_user[user_key]` |

The keys are SCD2 version keys, so a fact joins the product, user or category version that was
valid at the time (§78). To slice by the *current* attributes instead, filter
`dim_* [is_current] = TRUE` on a separate current-state dimension (a duplicate query with that
filter), or use the business id columns.

Mark `dim_date` as the date table (`dim_date[date]`). Sort `month_name` by `month`, and
`day_name` by `dim_date[date]`'s weekday.

## 3. Measures (DAX)

Conversion percentages are derived here, not stored (§87).

```DAX
Active Users        = DISTINCTCOUNT ( agg_user_activity[user_key] )
Sessions            = COUNTROWS ( fact_sessions )
Converted Sessions  = CALCULATE ( [Sessions], fact_sessions[converted] = TRUE () )
Session Conversion% = DIVIDE ( [Converted Sessions], [Sessions] )
Avg Session Minutes = AVERAGE ( fact_sessions[session_duration_seconds] ) / 60
Returning Users     =
    COUNTROWS ( FILTER ( VALUES ( fact_sessions[user_key] ),
        CALCULATE ( DISTINCTCOUNT ( fact_sessions[date_key] ) ) > 1 ) )
Products Viewed     = SUM ( agg_user_activity[unique_products_viewed] )

Funnel View         = SUM ( agg_conversion_funnel[product_view_sessions] )
Funnel Cart         = SUM ( agg_conversion_funnel[add_to_cart_sessions] )
Funnel Checkout     = SUM ( agg_conversion_funnel[checkout_started_sessions] )
Funnel Order        = SUM ( agg_conversion_funnel[successful_order_sessions] )
View→Cart %         = DIVIDE ( [Funnel Cart], [Funnel View] )
Cart→Checkout %     = DIVIDE ( [Funnel Checkout], [Funnel Cart] )
Checkout→Order %    = DIVIDE ( [Funnel Order], [Funnel Checkout] )
Abandonment %       = DIVIDE ( SUM ( agg_conversion_funnel[checkout_abandoned_sessions] ), [Funnel Checkout] )
Cancelled Sessions  = SUM ( agg_conversion_funnel[cancelled_order_sessions] )

GMV                 = SUM ( agg_daily_revenue[gross_merchandise_value] )
Discounts           = SUM ( agg_daily_revenue[discount_amount] )
Net Sales           = SUM ( agg_daily_revenue[net_transaction_sales] )
Cancelled Value     = SUM ( agg_daily_revenue[cancelled_order_value] )
Revenue After Canc. = SUM ( agg_daily_revenue[revenue_after_cancellations] )
Orders              = SUM ( agg_order_metrics[order_count] )
AOV                 = DIVIDE ( SUM ( agg_order_metrics[total_order_value] ), [Orders] )
Cancellation Rate   = DIVIDE ( SUM ( agg_order_metrics[cancelled_order_count] ), [Orders] )

Product Views       = SUM ( agg_product_performance[product_view_count] )
Units Sold          = SUM ( agg_product_performance[units_sold] )
Product Net Revenue = SUM ( agg_product_performance[net_revenue] )
View→Purchase 7d %  = DIVIDE ( SUM ( agg_product_attribution[converted_users] ),
                               SUM ( agg_product_attribution[viewing_users] ) )
```

Money columns are `DECIMAL(18,2)` in Databricks. Keep them as **Fixed decimal number** in
Power BI; never float (§111).

## 4. Pages

### Business Analytics (§104). No infrastructure visuals here (§103).

1. **Overview**: cards for Active Users, Sessions, Orders, Net Sales, AOV and Cancellation
   Rate, plus a Net Sales line by `dim_date[date]`.
2. **Customers & sessions**: sessions per day, returning users, avg session minutes, sessions
   by device type, and users by city (`dim_user[city]`, current).
3. **Funnel**: a funnel visual (View → Cart → Checkout → Order), step-conversion cards,
   abandonment %, and cancelled sessions.
4. **Products**: a table from `agg_product_performance` + `dim_product` (views, unique
   viewers, cart adds, unique cart users, orders, units, GMV, discount, net revenue), a
   category slicer, and 7-day conversion from `agg_product_attribution` (avg/median conversion
   time).
5. **Revenue & orders**: daily GMV / discounts / net sales / cancelled value / revenue after
   cancellations (`agg_daily_revenue`), plus confirmed vs cancelled orders and the cancellation
   rate (`agg_order_metrics`).

### Platform Observability (§103, §100 priority: health → latency → throughput → late data → failures)

1. **Health**: `pipeline_runs` (latest state, last success, failed flows), `cdc_connector_health`,
   and `pipeline_stage_metrics` by stage (Bronze / Silver Events / Silver CDC / Reference
   Resolution / Gold).
2. **Latency & throughput**: `latency_metrics` (ingestion / processing / end-to-end p50 and p95
   per hour), output records per stage, and `kafka_lag` per topic/partition with
   `partition_share`.
3. **Data quality & late data**: `data_quality_metrics` (quarantine by type, quarantine rate,
   decode failures, late / too-late) and `late_replay_status` (backlog, success, failures,
   latency).
4. **Reference resolution & recovery**: `reference_resolution_status` (backlog, oldest age,
   resolution latency, retries), `backfill_audit` and `reconciliation_results`.

## 5. What's in the data

All data comes from the real application. Simulated shoppers (`scripts/simulate_traffic.py`)
drive the same API the frontend uses; their emails and session ids start with `sim-`.
Verification and failure-test traffic uses the prefixes `p7…`–`p10…`, `ft-…` and
`bronze-verify`. Synthetic CDC test products (brand `zz-test`) are excluded from Gold.
